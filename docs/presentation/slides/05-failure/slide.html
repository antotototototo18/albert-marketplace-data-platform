Back-fill = re-running the pipeline for past days · runbook = our step-by-step incident guide, where both lessons now live

BENJAMIN, 2 min. Two things broke in our daily pipeline. First: re-loading past days. We call it a back-fill. We wanted to load the 15th and the 16th of September. Before running it, we wrote down our prediction: 468 new orders. We got 208. The 15th was missing. Why? A test run already existed for the 15th, but it covered the 14th. Airflow keeps one run per date, so it reused it and loaded the 14th again. We deleted that old run and ran again: 468, as predicted. Then we ran it a second time: zero new rows. That is what we want: running the same day twice changes nothing. Second: a bad row reached gold. This one was a drill: we planted one duplicate row on purpose. Our first design, the one from the course, built all the tables first and tested them after. So for a moment, gold showed 10 units and 87 euros 90 too many. The test caught it, but too late: an alarm, not a lock. We changed it. Now each table is tested right after it is built, and everything that depends on a failed test is skipped: 38 steps were skipped. Gold kept the right numbers: 1,201 units and 32,802 euros. Both lessons are now in our runbook, our incident guide. HANDOVER: Lenny closes with what we would do next.
